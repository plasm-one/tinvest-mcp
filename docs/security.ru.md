# Модель безопасности

*[English version](security.md)*

Этот документ описывает, что защищает `tinvest-mcp`, каким образом, и — то,
что обычно пропускают в подобных документах — **чего он не защищает**, с
указанием реально работающей меры в каждом случае.

Прочитайте его до подключения продового токена. Если читать только два раздела

## Чеклист усиления

В порядке убывания пользы.

- [ ] **Работайте в проде с read-only токеном и вообще без токена исполнения.**
      Оставьте `TINVEST_FULLACCESS_TOKEN` пустым. Тогда ордер выставить
      **невозможно** — не по политике, а структурно:
      `Settings.active_trade_token()` вернёт `None`, и `TInvestAdapter` упадёт
      с ошибкой до любого RPC. Это самая эффективная доступная вам мера, и она
      ничего не стоит.
- [ ] **Никогда не выдавайте скоуп на переводы денег.** Этот сервер не вызывает
      ни одного эндпоинта переводов. Токен, умеющий двигать деньги, превращает
      утечку файла в вывод средств.
- [ ] **Освойте процесс в `sandbox`.** Реальные ордера там невозможны, что бы
      ни сделала модель.
- [ ] **`chmod 600 .env`.** Это bearer-credential в текстовом файле.
- [ ] **Оставьте `transport = "stdio"`.** Нет порта — нет слушателя и нет
      локального атакующего.
- [ ] **Выставьте риск-лимиты сами** в `config.toml` и перепроверьте их после
      смены `mode` — см. [ловушку sandbox-значений в проде](#ловушка-sandbox-значений-в-проде).
- [ ] **Используйте `instrument_allowlist`**, если агенту нужна пара
      инструментов. Это самый жёсткий контроль в файле.
- [ ] **Не кладите токен в конфиг редактора.** `.vscode/mcp.json` и
      `.cursor/mcp.json` коммитятся и синхронизируются. Сервер читает `.env`
      именно затем, чтобы они оставались чистыми.
- [ ] **Не держите MCP-серверы с недоверенным контентом в одной сессии** с
      этим — см. [Prompt injection](#prompt-injection).
- [ ] **Иногда читайте `audit.jsonl`.** Это единственная запись о действиях
      агента, не зависящая от его собственного рассказа о них.
- [ ] **Запускайте `tinvest-mcp-doctor`** после каждого изменения конфигурации.
      Он печатает, какие файлы реально действуют и что взведено.

## Модель угроз

### В зоне защиты

| Угроза | Защита |
|---|---|
| Модель выставляет ордер, который пользователь не одобрял | Превью → явная отправка с перепроверкой по свежей котировке; реальная торговля выключена по умолчанию |
| Модель ошибается в объёме или цене | Жёсткие численные лимиты в `config.toml`, проверяются дважды; проверки отклонения цены и свежести котировки |
| Цену облигации в % от номинала приняли за рубли | Проверки `PRICE_DEVIATION` и `PRICE_INCREMENT`; единица измерения указана в каждом снапшоте |
| Утечка токена через логи или текст ошибки | Токены не логируются; `Settings.__repr__` их скрывает; типы ошибок не несут секретов; ключи, похожие на токен, вырезаются перед записью |
| Утечка токена через закоммиченный конфиг | Токены живут только в `.env`, он в gitignore и отделён от `config.toml` |
| Повторный вызов дублирует ордер | Ключ идемпотентности сохраняется **до** RPC (`services.py`) |
| Устаревшее одобрение исполняется позже | TTL превью (`confirmation_ttl_seconds`), TTL плана, `EXPIRED` — терминальный статус |
| Ордер уходит не на тот счёт | `require_single_account_token`; проба изоляции счёта на старте; модель никогда не передаёт id счёта |
| Шаг плана исполнен вне очереди или план обойдён | Заявки, привязанные к плану, отвергаются в `post_order`; исполнение последовательное, продажи первыми; застрявший шаг ставит план на паузу |
| Разгон цикла ордеров | Лимит дневного оборота, лимит на заявку, лимит веса позиции |
| Prompt injection через рыночный контент | В этом сервере нет инструментов новостей / sentiment / веб-запросов |
| Неаутентифицированный локальный доступ к серверу | По умолчанию stdio: слушателя нет вообще |
| MITM на канале до брокера | TLS с явным бандлом доверия, ограниченным этим процессом |

### Вне зоны защиты

| Угроза | Почему | Что делать |
|---|---|---|
| Скомпрометированная машина | Токен лежит на этом диске и читается вашим пользователем | Гигиена ОС, шифрование диска, отсутствие токена исполнения |
| Вредоносный MCP-клиент | Клиент доверенная сторона по построению | Пользуйтесь клиентами, которым доверяете |
| Вызывающий, притворяющийся «доверенным UI» | В MCP нет идентичности вызывающего — [см. ниже](#проблема-идентичности-вызывающего) | Работайте без токена исполнения |
| Сбой, отказ или rate limit на стороне брокера | Не в нашей власти | Ошибки показываются, а не глотаются |
| Рыночный риск | Это не свойство безопасности | Читайте [DISCLAIMER.md](../DISCLAIMER.md) |
| Компрометация зависимости | Обычный риск экосистемы | Ревью зависимостей; `uv lock` в своём развёртывании |

## Токен: где лежит и куда уходит

```
.env  (chmod 600, в gitignore)
  └─► os.environ, однократно, при первом чтении настроек
        └─► Settings.sandbox_token / readonly_token / fullaccess_token
              └─► TInvestAdapter._client(trade=…)  ──gRPC+TLS──►  invest-public-api.tbank.ru
```

Четыре свойства, которые стоит назвать прямо:

1. **Один получатель.** Токен уходит ровно на один хост — в собственный API
   Т-Банка, то есть тому, кто его и выпустил. Ни прокси, ни реле, ни
   телеметрии, ни какого-либо эндпоинта plasm.one. В репозитории нет пути
   кода, передающего токен куда-либо ещё; `grep -r "token" src/` читается
   быстро, если хотите проверить.
2. **Один файл.** Секреты только в `.env`. `config.toml` сознательно
   бессекретный, чтобы его можно было коммитить и вставлять в баг-репорты.
3. **Разделение по привилегиям.** Чтение идёт через `active_read_token()`,
   исполнение — через `active_trade_token()`, и это разные строки, если вы их
   так настроили. `startup_checks.py` предупредит, если они совпадают.
4. **Никогда не отображается.** `Settings.__repr__` печатает
   `tokens=<redacted>`. Id счёта маскируется в `200***456` функцией `mask()`.
   `audit.py` удаляет любой ключ метаданных, содержащий `token` или
   `authorization`, перед записью.

### Риск-лимиты нельзя переопределить через окружение

Все значения секции `[tinvest]` — режим, лимиты, флаги — читаются **только** из
`config.toml`, **без переопределения переменными окружения**. Это сознательная
асимметрия с настройками транспорта (которые env-переменные принимают):

> Лимит риска, который можно поднять случайной переменной окружения, — не лимит риска.

Чтобы изменить порог, нужно отредактировать файл на диске и перезапустить
сервер. MCP-клиент, выставляющий переменные окружения дочернему процессу, ваши
лимиты расширить не может.

### Ловушка sandbox-значений в проде

**Дефолты** лимитов зависят от режима, так что переход в прод их ужимает:

| | `max_order_rub` | `max_daily_turnover_rub` | `max_position_weight` |
|---|---|---|---|
| дефолт `sandbox` | 500 000 | 5 000 000 | 1.0 |
| дефолт `prod` | **1 500** | **3 000** | **0.40** |

Но **явное** значение в `config.toml` всегда побеждает дефолт. Отсюда сценарий
отказа: вы расслабили лимиты для экспериментов в песочнице, потом переключили
`mode = "prod"` — и унесли в прод 500 000 ₽ на заявку с комментарием
«relaxed for sandbox» над строкой.

При переключении **удаляйте** расслабленные значения, а не правьте их, и
запускайте `tinvest-mcp-doctor`: он печатает действующие лимиты и
предупреждает, когда большой лимит взведён вместе с реальной торговлей.

## Скоупы токена

Выбирается при создании токена в веб-интерфейсе брокера и потом не меняется —
нужно выпускать новый.

| Скоуп | Что с ним делает сервер | Рекомендация |
|---|---|---|
| **Только чтение** | всё, кроме выставления заявок | ✅ выбор по умолчанию |
| **Полный доступ** | выставляет лимитные заявки | ⚠️ только при осознанно взведённой реальной торговле |
| **Переводы / движение денег** | **ничего — не используется** | ❌ не выдавайте |

Токен T-Invest — это **bearer-credential**: без proof-of-possession и без
привязки к клиенту. Кто владеет строкой — тот и вы, с любого IP, пока вы её не
отозвали. Именно поэтому скоуп и есть главный контроль: read-only токен в чужих
руках — это раскрытие информации, а токен с переводами — потеря денег.

Отзыв мгновенный и бесплатный, в том же экране, где токен выпускался. Если
есть хоть сомнение в утечке — отзывайте. Цена — перевыпуск токена;
альтернатива — неограниченный риск.

## Слои защиты

Проверки живут в [`risk_engine.py`](../src/tinvest_mcp/risk_engine.py) — по
функции на правило, каждая возвращает именованную проверку. **Жёсткая**
значит, что ордер не пройдёт. **Совещательная** — что факт показывается
человеку для решения.

### Структурные — недостижимо в принципе

| Контроль | Настройка | Дефолт |
|---|---|---|
| Реальная торговля выключена | `mode` + `enable_real_trading` | `sandbox`, `false` |
| Нет credential для исполнения | отсутствие `TINVEST_FULLACCESS_TOKEN` | не задан |
| Только LIMIT-заявки | `allow_market_orders` | `false` |
| Без маржи | `allow_margin` | `false` |
| Без шортов | `allow_shorts` | `false` |
| Классы инструментов | `allowed_instrument_types` | `share, bond, etf` |
| Строгий allowlist инструментов | `instrument_allowlist` | пусто (выключен) |
| Изоляция одного счёта | `require_single_account_token` | `true` |

### Жёсткие численные проверки — на заявку

| Код | Правило |
|---|---|
| `MAX_ORDER_VALUE` | сумма заявки ≤ `max_order_rub` |
| `DAILY_TURNOVER` | оборот за день ≤ `max_daily_turnover_rub` |
| `POSITION_WEIGHT` | итоговая позиция ≤ `max_position_weight` портфеля |
| `SUFFICIENT_CASH` | денег хватает с учётом комиссии и НКД |
| `POSITION_EXISTS` | продаём только то, что реально есть и доступно к продаже |
| `PRICE_DEVIATION` | лимит в пределах `max_price_deviation_pct` от живой котировки |
| `PRICE_INCREMENT` | цена кратна шагу цены инструмента |
| `PRICE_POSITIVE` | нет нулевой или отрицательной цены |
| `MAX_LOTS` | в пределах брокерского `GetMaxLots` |
| `LIMIT_ORDERS_ONLY`, `NO_MARKET_ORDER` | тип заявки разрешён |
| `DIRECTION_ALLOWED` | нет шорта при выключенных шортах |
| `INSTRUMENT_TYPE_ALLOWED`, `INSTRUMENT_ALLOWLIST` | инструмент допущен |
| `API_TRADE_AVAILABLE`, `TRADING_STATUS` | брокер сейчас реально разрешает торговлю через API |
| `NOT_QUALIFIED_ONLY` | не инструмент «только для квалов» |
| `MARKET_SESSION` | не в клиринговую паузу и не вне сессии |

Рыночные данные старше `market_data_max_age_seconds` отвергаются сразу, так что
ни одна проверка не выполняется по устаревшей котировке.

### Проверки уровня плана — на итоговый портфель

| Код | Правило |
|---|---|
| `PLAN_STEP_CASH`, `PLAN_STEP_POSITION` | каждый шаг выполним в своей очереди |
| `PLAN_MIN_CASH` | сохраняется минимум денег |
| `PLAN_ISSUER_LIMIT`, `PLAN_SECTOR_LIMIT` | лимиты концентрации, масштабируются по размеру портфеля |
| `PLAN_ALLOCATION_MANDATE` | результат остаётся в целевом коридоре аллокации |
| `PLAN_CURRENCY_EXPOSURE` | лимит валютной экспозиции (совещательный без явного согласия) |

### Совещательные — показываются, но не блокируют

`LDV_WARNING` (продажа скоро лишит трёхлетней льготы), `CORPORATE_ACTION_SOON`
(близко оферта или погашение), `CURRENCY_EXPOSURE` (сделка добавляет валютный
риск), `TAX_IMPACT` (оценка НДФЛ).

Они проходят намеренно: это решения, которые принадлежат вам, а описания
инструментов предписывают модели их показывать, а не прятать.

### Проверки на старте

`startup_checks.py` запускается при загрузке, логирует каждую находку и
отдаёт их через тул `status`: реальная торговля выключена, токен для режима
есть, read- и trade-токены различаются, лимиты заданы, изоляция одного счёта, а
в проде со взведённой торговлей — немутирующая проба `GetAccounts` **через
trade-токен**, подтверждающая, что у него действительно полный доступ к тому же
набору счетов. Наличие секрета не доказывает, что им можно торговать; проба
проверяет.

Эти проверки **совещательные**: сервер всё равно стартует, чтобы работало
чтение. Жёсткие стопы стоят в момент исполнения.

## Путь исполнения

Что делает `post_order(proposal_id)`, по порядку
([`services.py`](../src/tinvest_mcp/services.py)):

1. **Проверка обхода плана.** Заявка, принадлежащая торговому плану,
   отвергается сразу — она должна идти через `execute_plan_step` с его двумя
   гейтами. Это закрывает очевидный обход подтверждения плана.
2. **Проверка TTL.** Истёк → `EXPIRED`, статус терминальный, исполнения нет.
   Цена, по которой одобряли, больше не настоящая.
3. **Проверка статуса.** Проходит только `READY_FOR_CONFIRMATION` (или
   состояние сверки); терминальные статусы отвергаются.
4. **Гейт реальной торговли.** В проде без `enable_real_trading` —
   `TInvestRealTradingDisabledError`. Независимо от стартовой проверки: этот
   гейт стоит в точке невозврата.
5. **Полная перепроверка.** Свежие данные инструмента, свежий рыночный
   снапшот, свежий портфель — и **вся** батарея риск-проверок заново. Превью,
   прошедшее по котировке двухминутной давности, исполниться не получит. Отказ
   → `RISK_REJECTED` плюс запись в аудит с кодами непрошедших проверок.
6. **Ключ идемпотентности сохраняется до RPC.** Повтор после таймаута не
   породит второй ордер.
7. **Запись в аудит перед вызовом**, затем заявка уходит как LIMIT по денежной
   цене, выведенной из проверенной котировки.

Торговые планы добавляют: `confirm_trade_plan(plan_id)` на всю корзину, затем
`preview_plan_step(plan_id)` → `execute_plan_step(plan_id)` на каждый шаг,
последовательно и с продажами первыми, где любой незавершённый или упавший шаг
ставит план на паузу и блокирует всё после него. Автопродолжения нет.

Обратите внимание, что несут вызовы исполнения: **только id**. Ни инструмент,
ни количество, ни цену. Условия заявки зафиксированы при создании превью и на
момент отправки не редактируются — модели, собравшей другую заявку между
превью и исполнением, просто некуда её положить.

## Prompt injection

Сложная проблема агентной торговли и та, которую код в этом репозитории не
решает полностью.

**Механизм.** Недоверенный текст, попавший в контекст модели, может попытаться
дать ей инструкцию. Модель с торговыми инструментами — модель, которую можно
убедить ими воспользоваться. Текст не обязан приходить из этого сервера:
веб-страница в другой вкладке той же сессии, документ, README, вывод другого
MCP-сервера, поле описания эмитента.

**Что делает этот сервер.** Он не предоставляет **ни новостей, ни sentiment,
ни аналитических комментариев свободным текстом, ни веб-запросов**. Это
сознательное отсутствие, а не недоделка: такие инструменты — стандартные
переносчики инъекций, и брокерский сервер — худшее место для их размещения.
Всё, что здесь возвращается, — либо число, посчитанное по структурным данным
брокера, либо короткое перечислимое поле.

Прогнозы аналитиков (`get_instrument_forecast`) — единственное место, где
входит сторонняя оценка от брокера, и она приходит структурными числовыми
полями: enum рейтинга, целевая цена, процент апсайда — не прозой.

**Чего он не может.** Он не видит остальную вашу сессию. Если вы поднимете
рядом MCP-сервер с браузером или новостями, вы собрали цепочку
«инъекция → сделка» внутри своего же клиента, и инструменты этого сервера
станут исполнительным механизмом нагрузки.

**Работающая мера: нет токена исполнения.** С research-креденшелами успешная
инъекция даёт атакующему состав вашего портфеля — плохо, но ограниченно, и это
не потеря денег. Любая защита на уровне промпта деградирует от новой
формулировки; отсутствующий credential — нет.

Вторая мера: `instrument_allowlist`. Даже при полностью взведённой торговле
агента, ограниченного проверенными вами инструментами, нельзя завести в чужую
неликвидную микрокапитализацию.

## Безопасность транспорта

### stdio — по умолчанию

Клиент запускает сервер дочерним процессом и общается через пайпы.
**Слушающего сокета нет**, значит подключаться нечему — ни локальному
процессу, ни браузеру, ни сети. Граница безопасности — граница процесса ОС.

Оставьте этот режим, если у вас нет конкретной причины его менять.

### HTTP — только осознанно

`transport = "http"` поднимает HTTP-сервер FastMCP. **У него нет собственной
аутентификации.** Всё, что дотягивается до порта, может вызвать любой
зарегистрированный инструмент, включая исполняющие, используя ваш токен. Ни
пароля, ни API-ключа, ни allowlist.

То есть открытый порт здесь — это не «HTTP API», а неаутентифицированный
эндпоинт удалённой торговли.

Два конкретных локальных риска даже на loopback:

* **Любой локальный процесс** под любым пользователем, дотянувшийся до
  `127.0.0.1:8003`, может торговать. На общей или многопользовательской машине
  loopback — не граница.
* **DNS rebinding.** Посещённую вами веб-страницу можно заставить разрешить
  имя хоста в `127.0.0.1` и обращаться к вашему локальному порту из браузера.
  Токен странице не достаётся — но достаётся **возможность**: странице не
  нужно воровать ваш credential, если она может позаимствовать ваш сервер.

Если HTTP всё-таки нужен:

1. Слушайте только `127.0.0.1`, никогда `0.0.0.0`. При другом адресе сервер
   печатает громкое предупреждение в stderr.
2. Поставьте перед ним реверс-прокси с настоящей аутентификацией (mTLS или
   прокси, подставляющий и проверяющий bearer-токен).
3. Работайте только на чтение. Не взводите реальную торговлю на HTTP-развёртке.
4. Предпочитайте контейнер без публикации порта.

### Про «токен могут перехватить в запросе»

Частая и разумная тревога, на которую стоит ответить точно: **и локальный
сервер, и удалённый хостируемый отправляют токен по TLS, и в обоих случаях
credential зашифрован на проводе.** Наблюдатель в сети видит хост назначения
(SNI), IP и размеры пакетов — но не токен. Перехват на проводе — не то, где
лежит содержательная разница между архитектурами.

Разница, которая действительно важна, — в том, *кто ещё хранит credential* и
*каков радиус поражения*:

* **Локально (этот сервер):** токен покоится в одном файле на вашем диске и в
  памяти одного процесса. Реалистичные векторы утечки — ваша машина и ваши же
  бэкапы.
* **Хостируемый MCP (любой вендор):** токен дополнительно покоится в
  MCP-конфиге вашего редактора — который регулярно коммитится в git,
  синхронизируется между машинами через settings sync и попадает в командные
  конфиги. Плюс он проходит ещё одну точку терминации TLS. Когда хост — **сам
  брокер**, новой доверенной стороны не появляется; когда третья сторона —
  появляется.

На практике токен, закоммиченный в репозиторий в `.vscode/mcp.json`, — куда
более вероятный инцидент, чем любая атака на канал. Именно поэтому этот сервер
читает `.env`, а не конфиг клиента, и именно поэтому
[docs/comparison.md](comparison.md) формулирует выбор так, как формулирует.

## TLS и российский УЦ

API Т-Банка предъявляет цепочку сертификатов российского национального УЦ
(«Russian Trusted Root / Sub CA», Минцифры), которого нет ни в `certifi`, ни во
встроенных корнях gRPC. Без него рукопожатие падает с
`CERTIFICATE_VERIFY_FAILED`.

[`tls.py`](../src/tinvest_mcp/tls.py) решает это, собирая бандл из публичных
корней (`certifi`) плюс российские корни и указывая на него gRPC через
`GRPC_DEFAULT_SSL_ROOTS_FILE_PATH`.

**Скажем прямо, что это значит.** Доверие дополнительному корневому УЦ означает,
что этот УЦ в принципе может выписать сертификат на **любой** хост, и ваш
клиент его примет. Это реальное расширение MITM-поверхности, принятое осознанно,
потому что иначе API недостижим.

Что его ограничивает здесь:

* Переменная выставляется **только внутри этого процесса**, на этапе импорта.
  Системное хранилище доверия не затрагивается; браузер и другие приложения не
  задеты.
* Она действует на **gRPC-каналы этого процесса** — а они в этом сервере ведут
  ровно на один хост.
* Заданный оператором `GRPC_DEFAULT_SSL_ROOTS_FILE_PATH` уважается и никогда не
  перезаписывается, а `[tinvest].ca_bundle` позволяет подставить свой бандл.

**Не устанавливайте российский корень в системное или браузерное хранилище
доверия**, чтобы заработал какой-то другой клиент. Это превращает узкое
решение, ограниченное процессом, в решение уровня всей машины. Ограниченность
процессом — и есть смысл того, как это реализовано.

## Логи, маскирование и журнал аудита

**Никогда и никуда не пишутся:** API-токены, заголовки авторизации,
немаскированные id счетов.

Механизмы:

* `Settings.__repr__` → `tokens=<redacted>`. Объект настроек в трейсбеке или
  отладочном принте не утечёт.
* `mask()` → `200***456`. Id счёта маскируется на каждой границе.
* `errors.py` — типизированные исключения, сообщения которых собираются из
  безопасных полей; брокерские ошибки при сомнении сводятся к имени типа.
* `audit.py` удаляет любой ключ метаданных со словом `token` или
  `authorization` перед записью, что бы туда ни передал вызывающий.
* Все логи идут в **stderr**. На stdio канал stdout — это протокол, и
  случайная строка лога там ломает поток MCP.

**Журнал аудита** ([`journal.py`](../src/tinvest_mcp/journal.py)) — файл JSONL
только на добавление, по объекту в строке: время, действие, id ордера, статус и
маскированный контекст. В него попадают `submit_order`, `submit_rejected`,
`revalidation_failed`, `account_isolation_violation`, исполнение шагов плана и
отмены — запись идёт **до** вызова брокера, так что действие, повисшее в
полёте, всё равно оставляет след.

Расположение: `[tinvest].audit_log`, относительный путь разрешается от
state-каталога (`$TINVEST_MCP_STATE_DIR`, иначе каталог самого конфига, иначе
`~/.local/state/tinvest-mcp`) — но **не** от рабочего каталога, который
MCP-клиент выбирает произвольно и который иначе разбросал бы ваш аудит по
нескольким файлам.

Запись в журнал никогда не выбрасывает исключение в поток вызывающего. К
моменту записи ордер уже дошёл до брокера, и потерять строку лога строго лучше,
чем упасть на завершённой сделке. Компромисс назван здесь, чтобы не стать
неожиданностью: заполненный диск стоит вам строк аудита, а не ордеров.

## Чего это не защищает

### Проблема идентичности вызывающего

**Самое важное честное ограничение в этом документе.**

Несколько описаний инструментов говорят, что ИИ-агент не должен вызывать
`post_order` и что исполнение принадлежит «доверенному UI или контроллеру
исполнения». **В MCP нет понятия идентичности вызывающего.** Сервер не может
отличить вызов, сделанный моделью, от вызова, сделанного человеком, нажавшим
«Подтвердить»: оба приходят одинаковым JSON-RPC по одному каналу.

Значит, эта инструкция — **политика уровня промпта, а не технический гейт.**
Модель, которая её проигнорирует, или инъекция, которая её перебьёт, могут
вызвать `post_order` напрямую. Не воспринимайте эту формулировку как границу
принуждения.

Что действительно принуждается и не зависит от того, кто вызывает:

* реальная торговля выключена, пока не выставлены два флага конфигурации;
* **нет credential для исполнения, если вы его не настроили** — решающий
  контроль;
* полная перепроверка риска по свежей котировке в момент отправки;
* TTL превью; отказ заявкам, привязанным к плану; лимиты на заявку и на день;
* вызовы исполнения принимают только id, никогда — условия заявки.

Мера, повторённая ещё раз, потому что она и есть весь ответ: **работайте в
проде без `TINVEST_FULLACCESS_TOKEN`.** Тогда `post_order` падает с ошибкой
конфигурации, кто бы его ни вызвал, и политика уровня промпта перестаёт иметь
значение.

### Всё остальное

* **Скомпрометированная машина = скомпрометированный счёт.** `.env` читается
  вашим пользователем. `chmod 600` останавливает других пользователей, а не
  вредоносный код, работающий от вашего имени.
* **Вредоносный или сломанный MCP-клиент** доверен по построению. У него пайп.
* **Зависимости.** `fastmcp`, `pydantic`, SDK T-Invest и их транзитивные
  зависимости работают в одном процессе с вашим токеном. Обычная экспозиция
  supply chain. Lock-файл в репозитории не поставляется — выполните `uv lock`
  в своём развёртывании, если нужны воспроизводимые сборки и смена зависимости,
  видимая в диффе.
* **Сторона брокера.** Rate limits, сбои, отказы по заявкам, изменения API и
  ограничения по счёту — вне контроля этого сервера. Ошибки показываются, а не
  глотаются, и это всё, что он может.
* **Рыночный риск — не свойство безопасности.** Все проверки здесь — это
  арифметика механики заявок. Ничто из этого не делает сделку хорошей идеей.

## Реакция на инцидент

**Если думаете, что токен утёк:** сначала отзовите его на
<https://www.tbank.ru/invest/settings/api/> — до всякого расследования. Отзыв
мгновенный и бесплатный. Потом читайте `audit.jsonl` на неожидаемые записи
`submit_order` и сверяйтесь с историей операций у брокера — она
авторитетна.

**Если появился неожиданный ордер:**

1. `get_order_state` / `list_executing_orders`, затем `cancel_order`, если он
   ещё не исполнен.
2. `audit.jsonl` — каждая отправка там, с маскированным контекстом и временем,
   записанная до того, как вызов ушёл.
3. Разоружить: `enable_real_trading = false` и убрать
   `TINVEST_FULLACCESS_TOKEN` из `.env`. Перезапустить сервер.
4. И только потом разбираться, как это произошло. Журнала плюс истории брокера
   достаточно, чтобы восстановить последовательность.

**Если не уверены, что взведено прямо сейчас:** `tinvest-mcp-doctor`.
